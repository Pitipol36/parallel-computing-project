## สไลด์ 1: หน้าปก (1:30)

สวัสดีทุกคน ชื่อ `[ชื่อเล่นหรือชื่อจริง]` โปรเจกต์นี้คือการทำ ray tracing โมเดล 3D ที่สแกนมาขนาดใหญ่บน GPU
ขอเริ่มจากเหตุผลว่าทำไมถึงเลือกหัวข้อนี้

ก่อนเรียนวิชานี้ เราเคยเขียน ray tracer ของตัวเองมาแล้ว ชื่อ RT-Project เขียนด้วย Python
เป้าหมายคือเรนเดอร์หลุมดำ มีจานพอกพูนมวล ดาวเคราะห์อีกสองสามดวง และยานสำรวจลำเล็ก ๆ
หลุมดำในนั้นเป็นของปลอม เพราะ engine ยิงได้แค่ ray เส้นตรง เราเลยดัด ray ที่ผ่านใกล้หลุมดำ
ให้โค้งเข้าหาจุดศูนย์กลาง ด้วยแรงดึงแบบมวลหารระยะทางกำลังสอง เหมือนแรงโน้มถ่วง

มันใช้งานได้ และเราก็ภูมิใจกับมัน แต่มันสอนอะไรบางอย่าง การหาว่า ray ชนอะไร scene ของเรา
วนลูปทดสอบวัตถุทุกชิ้น แล้วเก็บชิ้นที่ใกล้ที่สุดไว้ ถ้ามีแค่ทรงกลม วงแหวน และสี่เหลี่ยมราวสิบชิ้นก็ไม่มีปัญหา
เรายังแบ่งภาพเป็นแถว ๆ แล้วรันบน CPU ทุก core ด้วย แต่ถึงอย่างนั้น ภาพ 4K ที่ 1024 samples ต่อ pixel
ก็ยังใช้เวลา `[ใช้เวลาเท่าไร]`

เราเลยสงสัยว่า ถ้าจะเรนเดอร์วัตถุ *จริง ๆ* ต้องทำอย่างไร ไม่ใช่ทรงกลมสิบลูก แต่เป็นรูปปั้นที่สแกนด้วยเลเซอร์
มีสามเหลี่ยมเป็นล้านชิ้น ถ้าใช้ลูปแบบเดิม ray ทุกเส้นต้องทดสอบสามเหลี่ยมเป็นล้าน
สิ่งที่ต้องมีคือสองอย่างที่โปรเจกต์เก่าไม่มี อย่างแรกคือวิธีหาจุดชนที่ใกล้ที่สุดที่ฉลาดกว่าเดิม
นั่นคือ bounding volume hierarchy หรือ BVH อย่างที่สองคือฮาร์ดแวร์ที่ขนานกว่ามาก นั่นคือ GPU
สองอย่างนี้คือโปรเจกต์นี้

*[ชี้ไปที่มังกร]* นี่คือ Stanford dragon มีสามเหลี่ยม 871,000 ชิ้น GPU เรนเดอร์ภาพนี้ได้ในประมาณ 7 มิลลิวินาที

## สไลด์ 2: โจทย์ (0:40)

ทุก pixel ต้องยิง ray ออกไป primary ray หนึ่งเส้นหาว่า pixel นั้นมองเห็นอะไร shadow ray หนึ่งเส้น
ถามว่าจุดนั้นมองเห็นแหล่งกำเนิดแสงไหม และ ambient-occlusion ray อีก N เส้น ถามว่าจุดนั้นถูกล้อมรอบมากแค่ไหน
ซึ่งทำให้เกิดเงามืดนุ่ม ๆ ตามซอกต่าง ๆ

ที่ความละเอียด full HD กับ AO 4 samples จะได้ ray ประมาณ 12 ล้านเส้นต่อเฟรม และแต่ละเส้นต้องค้นหา
ในสามเหลี่ยมมากถึงล้านชิ้น ray แต่ละเส้นไม่ขึ้นต่อกัน จึงขนานได้มาก แต่การค้นหาแต่ละครั้งต้องเดินไปตาม tree
ที่ไม่สม่ำเสมอ ซึ่งเป็นรูปแบบที่ต่างจากแล็บของเรา ไม่ใช่ stencil ไม่ใช่ scan ไม่ใช่ reduction แต่เป็น tree traversal

## สไลด์ 4: Brute force (0:35)

*[ชี้ไปที่ลูป]* เริ่มจากวิธีที่ตรงไปตรงมาที่สุดก่อน สำหรับทุก pixel สร้าง ray จากกล้อง แล้ววนลูปทุกสามเหลี่ยม
ทดสอบว่า ray ชนสามเหลี่ยมไหม แล้วเก็บจุดชนที่ใกล้ที่สุดไว้ shadow ray กับ AO ray ใช้ลูปเดียวกัน
แต่หยุดทันทีที่เจอจุดชนแรก วิธีนี้ง่ายและถูกต้องเสมอ และมันก็คือลูปใน RT-Project ของเราเป๊ะ ๆ

ปัญหาคือต้นทุน ซึ่งเท่ากับจำนวน ray คูณจำนวนสามเหลี่ยม สำหรับ dragon คือ ray 12 ล้านเส้น
คูณสามเหลี่ยม 871,000 ชิ้น ได้ประมาณสิบยกกำลังสิบสามครั้งของการทดสอบ ray กับสามเหลี่ยมต่อเฟรม
แม้แต่บน GPU กระต่ายตัวเล็ก ๆ ที่ความละเอียด 320 x 240 ยังใช้เวลา 3.6 วินาที
ดังนั้นก่อนจะทำอะไรแบบขนาน เราต้องมีอัลกอริทึมที่ดีกว่านี้ก่อน

## สไลด์ 5: BVH เชิงลึก (0:40)

ต่อไปคือหัวใจของการนำเสนอนี้ BVH ทำงานอย่างไร และทำไมมันถึงชนะ

**ไอเดียหลัก** ถ้า ray ไม่ชนกล่อง มันก็ไม่ชนอะไรที่อยู่ข้างในกล่องนั้นเลย การทดสอบ ray กับกล่องที่ขนานกับแกน
ถูกมาก แค่ลบและคูณไม่กี่ครั้งต่อแกน เพื่อหาว่า ray เข้าและออกจากแผ่น slab แต่ละคู่ตรงไหน แล้วเปรียบเทียบ
เราจึงเอากล่องไปครอบกลุ่มของสามเหลี่ยม และเมื่อ ray พลาดกล่องไป การทดสอบถูก ๆ ครั้งเดียวก็ตัดสามเหลี่ยม
ทิ้งได้เป็นพัน ๆ ชิ้น

## สไลด์ 6: สร้าง BVH อย่างไร (1:30)

*[แผนภาพ: สามเหลี่ยมสิบสองชิ้น root กล่อง A กับ B และ leaf สี่อัน tree อยู่ทางขวา]*

**โครงสร้าง** ทำแบบนี้ซ้ำแบบ recursive ก็จะได้ tree กล่อง root ครอบทั้งโมเดล แต่ละ node แบ่งสามเหลี่ยมของตัวเอง
เป็นสองกลุ่ม แล้วเอากล่องที่พอดีไปครอบแต่ละกลุ่ม แบ่งต่อไปเรื่อย ๆ จนแต่ละ leaf เหลือสามเหลี่ยมแค่ไม่กี่ชิ้น
สำหรับ dragon จะได้ 959,000 node มี leaf ราว 480,000 อัน แต่ละอันมีสามเหลี่ยมไม่ถึงสองชิ้น และลึก 26 ชั้น

สังเกตว่าเราแบ่ง *วัตถุ* ไม่ได้แบ่ง *พื้นที่* สามเหลี่ยมแต่ละชิ้นอยู่ใน leaf เดียวเท่านั้น และกล่องพี่น้องสองกล่อง
ซ้อนทับกันได้ นี่คือความต่างจาก kd-tree หรือ grid ซึ่งตัดพื้นที่โดยตรง และต้องก๊อปสามเหลี่ยมที่คร่อมรอยตัด

**เลือกจุดแบ่งอย่างไร: Surface Area Heuristic** คุณภาพของ tree มาจากตรงนี้ เราอาจแบ่ง node ตรงกลางกล่อง
หรือแบ่งที่สามเหลี่ยมตัวกลาง (median) ก็ได้ แต่จุดแบ่งที่ดีที่สุดขึ้นกับ ray หลักการคือ ถ้า ray สุ่มเส้นหนึ่งชนกล่องแม่
โอกาสที่มันจะชนกล่องลูกด้วย ประมาณเท่ากับพื้นที่ผิวของกล่องลูกหารด้วยพื้นที่ผิวของกล่องแม่
ต้นทุนที่คาดหวังของการแบ่งแต่ละแบบจึงเป็น:

> cost = ต้นทุน traversal หนึ่งขั้น + (area_left / area_parent) × triangles_left
> + (area_right / area_parent) × triangles_right

เราลองจุดแบ่งที่เป็นไปได้หลาย ๆ จุด แล้วเก็บอันที่ถูกที่สุด ถ้าไม่มีจุดแบ่งไหนดีกว่าการทดสอบสามเหลี่ยมทั้งหมดตรง ๆ
node นั้นก็กลายเป็น leaf SAH ชอบกล่องเล็กและแน่นที่มีสามเหลี่ยมเยอะ และหลีกเลี่ยงกล่องใหญ่ที่ว่างเปล่า
ซึ่ง ray ชนไปก็เสียเปล่า

**ทำให้สร้างเร็ว: binning** การลองทุกจุดแบ่งที่เป็นไปได้ช้ามาก เราจึงใช้ binning ในแต่ละแกน เราโยนจุดศูนย์กลาง
ของสามเหลี่ยมลงใน 16 ช่อง (bin) แล้วกวาดหนึ่งรอบจากซ้ายและหนึ่งรอบจากขวา ซึ่งให้คะแนนระนาบแบ่งทั้ง 15 ระนาบ
ได้ในเวลาเชิงเส้นต่อ node การสร้างทั้งหมดจึงเป็น N log N ส่วน dragon สร้างเสร็จในประมาณ 0.8 วินาทีบน core เดียว

## สไลด์ 7: ray เดินผ่าน BVH อย่างไร (0:50)

**Traversal** *[ไล่ตาม ray บนแผนภาพทีละขั้น]* ray เริ่มที่ root แล้วทดสอบกล่องของลูกทั้งสองฝั่ง
มันเข้าไปในลูกที่ *ใกล้กว่า* ก่อน และ push ลูกที่ไกลกว่าลงใน stack เล็ก ๆ พร้อมระยะที่ ray จะเข้ากล่องนั้น
เมื่อ ray ชนสามเหลี่ยมที่ระยะ t แล้ว กล่องไหนที่ ray เข้าไปไกลกว่า t ย่อมไม่มีจุดชนที่ใกล้กว่า
เราจึงข้ามกล่องนั้นไป ทั้งตอนที่เจอมันครั้งแรก และตอนที่ pop มันออกจาก stack

shadow ray กับ AO ray ต้องการแค่จุดชน *ใดก็ได้* ไม่ต้องเป็นจุดที่ใกล้ที่สุด จึงหยุดทันทีที่ชนสามเหลี่ยมชิ้นแรก

## สไลด์ 8: ทำไมนี่คือเวอร์ชัน sequential ที่ดีที่สุด (0:35)

**ทำไมนี่คือเวอร์ชัน sequential ที่ดีที่สุด** SAH BVH คือโครงสร้างเร่งความเร็วมาตรฐานทั้งใน renderer
ที่ใช้งานจริงและในงานวิจัย node ถูกแปลงเป็น array เรียงแบบ depth-first ขนาด node ละ 32 byte
ลูกซ้ายจึงเป็น node ถัดไปเสมอ ขอบของสามเหลี่ยมและค่าส่วนกลับของทิศทาง ray ถูกคำนวณไว้ล่วงหน้า
มีสิ่งที่เจอที่น่าสนใจอย่างหนึ่ง Visual Studio compile `fminf` เป็นการเรียกฟังก์ชัน
พอเปลี่ยนเป็นการเปรียบเทียบธรรมดา ทั้งการเรนเดอร์และการสร้าง tree เร็วขึ้นประมาณหกเท่า

**ทำไมถึงดีกว่า: ดูที่ตัวเลข** ตอนนี้ ray แต่ละเส้นเยี่ยมชม node ประมาณ log N อัน ซึ่งราว ๆ ความลึกของ tree
คือ 26 แทนที่จะเป็นสามเหลี่ยม 871,000 ชิ้น ต้นทุนรวมจึงเปลี่ยนจาก ray คูณสามเหลี่ยม เป็น ray คูณ log ของ
จำนวนสามเหลี่ยม *[ย้อนกลับไปสไลด์ 4 หรือแค่พูดตัวเลข]* วัดบน bunny: brute force บน **GPU** ใช้ 3.6 วินาที
ส่วน BVH บน **CPU core เดียว** ใช้ 38 มิลลิวินาที อัลกอริทึมที่ดีบน core เดียว ชนะอัลกอริทึมที่แย่บน GPU
สองพัน core ได้ประมาณร้อยเท่า นี่คือเหตุผลที่เราสร้าง BVH ก่อน แล้วค่อยทำให้ขนานทีหลัง

และนี่ก็เป็นเหตุผลที่ GPU สมัยนี้มีฮาร์ดแวร์สำหรับ ray tracing โดยเฉพาะ RT core ของ NVIDIA เดินผ่าน tree
แบบนี้เลย ส่วนในโปรเจกต์นี้ เราเขียน traversal เองด้วย CUDA ทั้งหมด ไม่ได้ใช้ library ray tracing ใด ๆ

## สไลด์ 9: การออกแบบแบบขนาน (1:00)

แล้วมันรันบน GPU อย่างไร เราสร้าง BVH ครั้งเดียวบน CPU ด้วยโค้ดเดียวกับ baseline แล้ว upload ขึ้นไป
จากนั้น thread แต่ละตัวบน GPU รับผิดชอบ pixel หนึ่ง pixel และ trace primary ray, shadow ray และ AO ray ของมัน
โดยแต่ละเส้นมี stack เล็ก ๆ ของตัวเอง

เพื่อให้การเปรียบเทียบยุติธรรมและตรวจสอบได้ โค้ดส่วน ray, กล่อง, สามเหลี่ยม, traversal และ shading
ถูกเขียน *ครั้งเดียว* เป็นฟังก์ชัน `__host__ __device__` CPU กับ GPU จึงรันโค้ดเดียวกันจริง ๆ
ตัวเลขสุ่มสำหรับ AO มาจากการ hash หมายเลข pixel กับหมายเลข sample ทั้งสองฝั่งจึงยิง ray เหมือนกันทุกเส้น

thread ไม่ต้องสื่อสารกันเลย ต้นทุนจริง ๆ อยู่ที่ divergence คือเมื่อ thread ใน warp เดียวกันเดินคนละทางใน tree
และการอ่าน memory ที่กระจัดกระจาย

## สไลด์ 10: kernel สี่แบบ (0:55)

เพื่อดูว่าการ optimize แต่ละอย่างได้ผลเท่าไร เราเขียน kernel สี่แบบ brute force ทดสอบทุกสามเหลี่ยม
kernel BVH แบบ naive ใช้ tree เดียวกัน แต่เก็บข้อมูลเป็น struct ธรรมดา kernel แบบ optimized อ่านข้อมูล
แบบ `float4` ที่ align แล้วผ่าน read-only cache ใช้ส่วนกลับของทิศทาง และเข้าลูกที่ใกล้กว่าก่อน
ส่วน kernel แบบ persistent threads ปล่อย warp ออกมาแค่พอเต็ม GPU แล้วให้แต่ละ warp หยิบ tile ของ pixel
จากตัวนับ atomic กลาง

*[ชี้ไปที่ตาราง]* บนโมเดลที่ใหญ่ที่สุด คือ Buddha สามเหลี่ยม 1.09 ล้านชิ้น ที่ full HD kernel แบบ optimized
ใช้ 8.3 มิลลิวินาที ส่วน CPU core เดียวใช้ 937 มิลลิวินาที

## สไลด์ 11: ความถูกต้อง (0:40)

บน dragon มี pixel ต่างกันแค่ 7 จาก 307,000 pixel และทั้งหมดอยู่บนขอบสามเหลี่ยมพอดี ซึ่งเป็นจุดที่
fused multiply-add ของ GPU ปัดเศษต่างไป ภาพตรงกันที่ 56.7 เดซิเบล บน scene ทดสอบทุก pixel ชนสามเหลี่ยมชิ้นเดียวกัน
และ unit test ผ่านครบทั้ง 216 ข้อ รวมถึงการตรวจ BVH ทุกแบบเทียบกับ brute force ด้วย ray สุ่ม

## สไลด์ 16: เวลาไปอยู่ที่ไหน (0:35)

เมื่อการเรนเดอร์ใช้เวลาแค่ไม่กี่มิลลิวินาที การสร้าง BVH แบบ single thread ก็กลายเป็นต้นทุนที่ใหญ่ที่สุด
เกือบหนึ่งวินาทีบน Buddha และ block ที่เล็กหรือกว้าง เช่น 8 x 8 เร็วกว่าเล็กน้อย เพราะ pixel ที่อยู่ใกล้กัน

## สไลด์ 17: ต่อยอด: สร้าง BVH บน GPU (0:40)

*[ชี้ไปที่เส้นของ CPU ด้านบนของกราฟ]* ผลลัพธ์สุดท้ายเมื่อกี้คือจุดเริ่มของงานต่อยอด การสร้าง tree แบบ single thread
กลายเป็นเวลาส่วนใหญ่ก่อนได้ภาพแรก เราจึงสร้าง BVH บน GPU เริ่มจาก LBVH ของ Karras สามเหลี่ยมทุกชิ้นได้ Morton code
radix sort เรียงมันตามเส้นโค้งเติมเต็มพื้นที่ thread หนึ่งตัวต่อ node สร้างลำดับชั้น แล้ว pass จากล่างขึ้นบนที่ใช้ตัวนับ atomic
ก็คำนวณกล่อง บน dragon ใช้ไม่ถึง 5 มิลลิวินาทีแทนที่จะเกือบหนึ่งวินาที เร็วกว่าการสร้าง SAH บน CPU 160 เท่า
และเร็วกว่าอัลกอริทึมเดียวกันบน core เดียว 67 เท่า ทุก builder บน GPU มีคู่แฝดแบบ single thread และเราตรวจว่า tree
ของ GPU เหมือนกันทุกประการ

## สไลด์ 18: ราคาที่ต้องจ่าย: tree ที่หลวมกว่า (0:40)

ความเร็วมีราคา ลำดับ Morton ไม่ดูพื้นที่ผิวเลย กล่องจึงหลวมกว่า บนโมเดลสแกน tree แพงกว่า 19 ถึง 30 เปอร์เซ็นต์ตาม SAH
ray ทดสอบกล่องมากขึ้นราวหนึ่งในห้า และเรนเดอร์ช้าลง 12 ถึง 21 เปอร์เซ็นต์ *[ชี้แถว mixed sizes]* บน scene
ที่สามเหลี่ยมขนาดต่างกันมากจะแย่กว่านั้นเยอะ แต่มันสำคัญก็ต่อเมื่อ tree เดียวถูกใช้กับ ray จำนวนมาก tree แบบ SAH
จะตามทันหลังประมาณ 6.5 พันล้าน ray หรือราว 500 เฟรม full HD

## สไลด์ 19: เอาคุณภาพกลับมา: PLOC และ TRBVH (0:45)

builder คุณภาพสูงสองตัวบน GPU เอาคุณภาพนั้นกลับมา PLOC รวมกลุ่มจากล่างขึ้นบน แต่ละ cluster หาเพื่อนบ้านที่ใกล้ที่สุด
ในลำดับ Morton คู่ที่เลือกกันและกันจะรวมกัน แล้ว scan ที่เราเขียนเอง ซึ่งเป็นรูปแบบเดียวกับแล็บ scan ก็บีบรายการให้แน่น
ได้ tree ที่ห่างจากดีที่สุดไม่เกิน 12 เปอร์เซ็นต์ TRBVH เริ่มจาก LBVH แล้วใต้ node ใหญ่ทุกตัว หารูปร่างที่ดีที่สุดของ
treelet เจ็ดกิ่งด้วย dynamic programming เล็ก ๆ ใช้ warp หนึ่งตัวต่อ treelet ได้ห่างไม่เกิน 6 เปอร์เซ็นต์ ใน 70 มิลลิวินาที

## สไลด์ 20: H-PLOC: คุณภาพแบบ PLOC ใน kernel launch เดียว (0:40)

จุดอ่อนของ PLOC คือ loop บน dragon มี 68 รอบ แต่ละรอบเรียก kernel หลายครั้งและอ่านค่ากลับไปที่ CPU H-PLOC
ซึ่งตีพิมพ์ปีที่แล้ว สร้างทั้ง tree ใน launch เดียว thread ปีนขึ้นลำดับชั้น Morton จาก leaf แต่ละ node ถือรายการ cluster สั้น ๆ
และเมื่อรายการของลูกสองตัวรวมกันเกินสิบหก warp ทั้งตัวจะรวมมันใน shared memory คุณภาพเท่า PLOC
แต่เร็วกว่า 1.4 ถึง 4 เท่า ในเปเปอร์ใช้เวลามากกว่า LBVH ราว 15 เปอร์เซ็นต์ ของเราใช้ 1.4 ถึง 1.9 เท่าของ LBVH
และเรารู้ว่าเวลาหายไปที่ไหน

## สไลด์ 21: scene ที่ยากขึ้นและมาตรฐานที่ดีขึ้น (0:45)

*[ชี้ไปที่ภาพ]* โมเดลสแกนเป็นกรณีง่าย เพราะสามเหลี่ยมทุกชิ้นขนาดพอ ๆ กัน เราจึงเพิ่ม scene ที่ขนาดปนกัน มีสามเหลี่ยมพื้นขนาดใหญ่
เสาบาง ๆ และวัตถุหลายขนาด และเปลี่ยนมาตรฐานจาก binned SAH เป็น full sweep ที่ลองทุกจุดแบ่ง บนโมเดลสแกน binning
ห่างจากมันไม่ถึงหนึ่งเปอร์เซ็นต์ แต่บน scene ปนขนาดแย่กว่า 11 เปอร์เซ็นต์ และ **TRBVH ชนะตัวสร้าง SAH บน CPU**
ทั้งที่สร้างเร็วกว่า 16 เท่า เรายังทำให้การจับเวลายุติธรรมขึ้นด้วย warm-up วัด 11 รอบสลับกันและใช้ค่ามัธยฐาน
แต่ล็อก clock ไม่ได้ถ้าไม่มีสิทธิ์ admin ข้อสรุปเรื่องคุณภาพจึงอิงกับ SAH cost และตัวนับ traversal ซึ่งให้ผลแน่นอนทุกครั้ง

## สไลด์ 22: ความเร็วในการสร้าง เทียบกับคุณภาพ tree (0:40)

builder ทั้งหมดบนกราฟเดียว เวลาสร้างเทียบกับคุณภาพ tree ยิ่งไปมุมล่างซ้ายยิ่งดี builder บน GPU ทุกตัวอยู่บนแนวหน้า
LBVH เร็วที่สุดและหลวมที่สุด H-PLOC เป็นทางสายกลาง และ TRBVH ใกล้มาตรฐานที่สุดทั้งที่ยังสร้างเร็วกว่า CPU 13 ถึง 16 เท่า
builder ที่เหมาะจึงขึ้นกับว่า tree เดียวจะถูกใช้กับ ray มากแค่ไหน

## สไลด์ 23: Parallel reinsertion: ดีกว่ามาตรฐานบน CPU (0:40)

ขั้นสุดท้ายใช้ได้กับ tree ทุกแบบที่ผ่านมา parallel reinsertion ถามทุก node พร้อมกันว่า ถ้าย้าย node นี้ไปไว้ที่อื่นใน tree
ตรงไหนจะลด SAH cost ของทั้ง tree ได้มากที่สุด การย้ายที่ไม่แตะ node เดียวกันทำพร้อมกันได้ แต่ละการย้ายล็อก node
หกตัวของมันด้วย atomic max ตัวที่ชนะได้ย้าย แล้ว refit กล่องใหม่ หลังแปดรอบ tree จาก GPU ทุกแบบห่างจาก full sweep
ไม่กี่เปอร์เซ็นต์บนโมเดลสแกน และ TRBVH บวก PRBVH ชนะมันด้วย บน scene ปนขนาด ทั้งสี่แบบ **ดีกว่า** full sweep
5 ถึง 15 เปอร์เซ็นต์ เพราะ full sweep ยังเลือกแบบ greedy ที่ส่วนบนของ tree H-PLOC บวก PRBVH สร้าง tree ของมังกร
ใน 150 มิลลิวินาที ได้ tree ที่ดีกว่าตัวสร้างบน CPU ที่ใช้ 770 การเรนเดอร์เร็วขึ้น 16 ถึง 42 เปอร์เซ็นต์
เวลาที่เพิ่มขึ้นจึงคุ้มหลัง 11 ถึง 50 เฟรม

## สไลด์ 24: scene ที่เคลื่อนไหว: สร้างใหม่ทุกเฟรม (0:30)

*[ปล่อยให้ภาพเคลื่อนไหวเล่น]* ที่การสร้างเร็วสำคัญจริง ๆ คือ scene ที่เปลี่ยนทุกเฟรม มังกรระเบิดออก การ refit tree เดิม

ทุกเฟรมทำให้ tree ยังดีอยู่ที่ 17 ถึง 56 เฟรมต่อวินาที ส่วน CPU ต้องใช้ราวหนึ่งวินาทีต่อเฟรม

## สไลด์ 25: ข้อจำกัดและงานต่อไป (0:25)

เวลาส่วนใหญ่ของ PRBVH อยู่ที่การค้นหาแบบละเอียดทั่วทั้ง tree ถ้าค้นแค่รอบ ๆ แต่ละ node จะเสียคุณภาพนิดเดียวแต่ประหยัดเวลาได้มาก

สรุปคือ การไปจาก ray tracer Python ที่มีทรงกลมสิบลูก ไปสู่สามเหลี่ยมเป็นล้านชิ้น ต้องใช้สองขั้น

## คำถามที่น่าจะเจอ

- **ทำไมใช้ BVH ไม่ใช้ kd-tree หรือ grid?** สามเหลี่ยมแต่ละชิ้นถูกเก็บครั้งเดียว memory จึงมีขอบเขต
  (ไม่เกิน 2N − 1 node) สร้างได้เร็ว และรับมือกับความหนาแน่นของการสแกนที่ไม่สม่ำเสมอได้ดี
  grid แบบสม่ำเสมอเปลือง cell ไปกับพื้นที่ว่าง ส่วน kd-tree ต้องก๊อปสามเหลี่ยมที่คร่อมระนาบแบ่ง
- **ทำไมผลหลักสร้าง BVH บน CPU?** เพื่อให้การเปรียบเทียบยุติธรรม ทั้งสองเวอร์ชันใช้ tree เดียวกันทุกประการ
  ส่วนต่อยอด (สไลด์ 17–24) จึงสร้างบน GPU
- **รู้ได้อย่างไรว่า builder บน GPU ถูกต้อง?** แต่ละตัวมีคู่แฝดบน CPU แบบ single thread ที่รันโค้ดร่วมชุดเดียวกัน
  และ tree จาก GPU ต้องเหมือนกันทุก byte ทุก tree ต้องให้สามเหลี่ยมต่อ pixel เหมือน tree แบบ SAH และ
  `compute-sanitizer` ต้องไม่เจอ error หรือ race
- **ทำไม H-PLOC ของเราช้ากว่าในเปเปอร์?** เวลาส่วนเกินราวครึ่งหนึ่งคือการรวมระดับ warp เอง อีกส่วนคือขั้น flatten
  เพราะ id ของ node มาจากตัวนับ atomic ทำให้ tree กระจัดกระจายใน memory เปเปอร์รวมขั้นยุบ leaf เข้าไปในการสร้าง
  ซึ่งเรายังไม่ได้ทำ
- **ทำไม binned SAH ไม่ใช่ 100 %?** binning ลองแค่ 15 ระนาบต่อแกน บนโมเดลสแกนเสียไปราว 1 % แต่บนสามเหลี่ยม
  ขนาดปนกันเสีย 11 % ส่วน full sweep ลองทุกจุดแบ่ง
- **ทำไม persistent threads ไม่ช่วย?** เทคนิคนี้มาจาก GPU รุ่นเก่าที่ block scheduler จัดการงานไม่สม่ำเสมอได้ไม่ดี
  scheduler ของ Turing เติมงานให้ SM ได้เร็วอยู่แล้ว ตัวนับ atomic จึงเพิ่มแค่ overhead
- **180 เท่ายุติธรรมไหม ในเมื่อ CPU มี 8 core?** โจทย์ให้เทียบกับโค้ด sequential และ baseline ตั้งใจให้เป็น
  single thread ถึงจะ scale บน 8 core ได้สมบูรณ์แบบ GPU ก็ยังเร็วกว่าประมาณ 15–20 เท่า
- **ray หนึ่งเส้นเยี่ยมชมกี่ node จริง ๆ?** ประมาณความลึกของ tree (ราว 20–26) ตามเส้นทางของมัน บวกกิ่งข้าง ๆ
  ที่ตัดทิ้งไม่ได้ คือทดสอบกล่องไม่กี่สิบครั้งกับสามเหลี่ยมไม่กี่ชิ้น เทียบกับการทดสอบสามเหลี่ยม 871,000 ครั้ง
  ถ้าไม่มี tree
